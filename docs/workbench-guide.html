01这是什么

一个文件，就是整个应用。

「学习工作台」是一个为秋招备考设计的打卡应用，全部代码（HTML + CSS + JS）打包在 一个约 60KB 的 HTML 文件里。它没有后端、没有框架、没有 npm install——双击文件就能运行，丢到任何静态服务器上也能运行。

它的核心思路是：计算与存储全部发生在你自己的浏览器里。你看到的每一个进度条、每一张热力图，都是本机实时算出来的；你的每一条打卡记录，都写在你本机浏览器的 IndexedDB 里。服务器（如果有的话）只负责把这份 HTML 原样递给你，此后它就退场了。

02功能一览

四个页签，覆盖「打卡 → 计划 → 复盘」的完整闭环。

今日打卡

四个打卡组（每组带独立进度条与时间段）+ 三个复盘文本框（反思 / 心得 / 调整），支持任意日期回填。

补签

漏签速览面板（近 8 周网格）一眼看清哪几天断了；点格即可补签，勾选哪些项自己定。补签日在热力图上以 ⚑ 斜纹标记，与真实打卡可区分，随时可撤销。补签仅用于回填已过去的日期 —— 当天请在「今日」页正常打卡。

计划管理

计划项的增删改与归档，支持 Pointer Events 拖拽排序——鼠标和触屏统一处理，拖动时显示绿色插入指示线。

统计与热力图

打卡率、连续天数、GitHub 风格热力图，以及一张 50/30/20 的「能量条」展示时间分配。

学习日志

按类型（反思 / 心得 / 调整）筛选的历史记录流，每条带彩色左边框，快速回顾过去的复盘。

导入导出

一键导出 JSON / CSV 备份，随时导入恢复；数据迁移、设备更换都靠它兜底。

多设备云同步

基于 GitHub Gist 的同步层：多台设备围绕同一份云端数据读写，8 秒防抖自动上传 + 时间戳冲突保护。

03技术架构：三层分工

「分发」与「运行」彻底分离，每一层只做一件事。

分发层

固定网址 · CloudStudio 沙箱

云端一台常在线的小机器，跑着一个只会「读文件原样返回」的静态服务器，把 index.html 递给任何访问者，并映射一个固定域名。它不执行任何业务逻辑——只是文件快递员。

运行层

浏览器里的单文件应用

访问者拿到 HTML 副本后，渲染、打卡、统计、拖拽全部在本机执行。内部由三块组成：renderXxx 渲染函数（4 个页签）、Store 串行写队列（所有写操作的必经之路）、CloudSync 同步模块。

存储层

IndexedDB（本地） + GitHub Gist（云端）

本地是三张仓库：planItems（计划项）、days（每日打卡）、meta（配置与时间戳）。云端是一个 secret Gist 里的 JSON 文件，作为所有设备共享的「数据真相」。

04数据存在哪：IndexedDB 与串行写队列

所有可靠性的地基。

IndexedDB 是浏览器提供的本地数据库，数据按「协议 + 域名 + 端口」隔离。这意味着：

  • 关闭页面、重启电脑，数据都在——它是持久化的，不象 localStorage 那样容易被清
  • 本地 file:// 打开和线上网址打开是两个「源」，各自一个空仓库——换源必须用导出 JSON → 导入迁移一次，这不是 bug，是浏览器安全模型的设计
  • 不支持 IndexedDB 的老环境会自动降级到 localStorage（约 5MB 上限），并在界面上给出提示

为什么要有串行写队列

IndexedDB 的所有操作都是异步事务。如果打卡、改计划、拖拽排序同时触发多个写事务，就会出现竞态。所以应用里所有写操作都经过 Store.enqueue 排队串行执行：

// 所有写操作的必经之路：串行队列 + 时间戳 + 同步钩子
function enqueue(fn, silent){
  chain = chain.then(fn).then(res => {
    if(silent) return res;
    state.meta.lastLocalWrite = Date.now();   // ① 记录最后修改时间
    return DataLayer.put('meta', {...}).then(() => res);
  }).then(res => {
    if(!silent && CloudSync) CloudSync.scheduleAutoPush(); // ② 启动同步定时器
    return res;
  });
}

这个队列顺手做了两件事：给每次用户写入盖上 lastLocalWrite 时间戳（后面冲突保护要用），并启动云同步的防抖定时器。而 silent 参数是同步机制的关键——后面会讲。

05多设备同步：三层递进

部署解决「随时打开」，Gist 解决「数据跟着走」，时间戳保证「互不覆盖」。

多设备的本质困难只有一句话：IndexedDB 按源隔离，每台设备的浏览器各有一个独立仓库，互相看不见。解法是三层递进，每层解决一个问题：

层级解决的问题实现方式
① 固定网址随时打开单文件部署到 CloudStudio 沙箱，手机平板电脑收藏同一个地址
② Gist 云存储数据跟着人走所有设备读写 GitHub Gist 里的同一个 JSON 文件
③ 时间戳对账不覆盖别人的改动上传前比对云端时间与本机 csSyncedAt，宁可停下不盲写

为什么选 GitHub Gist 当云端

纯前端应用直连第三方存储有一道硬门槛——CORS（跨域资源共享）。浏览器同源策略下，只有对方服务器明确返回 CORS 响应头，页面里的 JS 才能跨域调用它的 API：

  • api.github.com：官方支持 CORS，浏览器可直接调用，免费，Gist 本质是账号下的一个云盘 JSON，带完整 REST API → ✓ 入选
  • 坚果云 WebDAV：服务器不返回浏览器跨域头，纯前端单文件无法直连 → ✗ 被否
  • 自建后端：能做，但违背「零依赖单文件」的初衷 → ✗ 不值得

同步的内容是整包数据：计划项 + 每日打卡 + 配置（过滤凭证后）。首次上传时自动创建一个 secret gist（不公开、无链接搜不到），之后每次 PATCH 整体替换文件内容。

多设备自动关联：新设备只有 token、还没有 gistId 时，工作台会先在你 GitHub 账号下搜索已有的同步 Gist（按描述匹配、取最近更新的一份）并自动关联——认不出已有数据时才会新建。这样同一 token 的所有设备永远读写同一份云端数据，不会各写各的 Gist。

自动上传：8 秒防抖

打卡往往是连续勾好几个框。如果每勾一次就发一次 PATCH，既浪费请求又容易触发 GitHub 限流。所以写入队列只负责启动/重置一个 8 秒定时器——连续操作不断重置定时器，直到你停下来 8 秒后，才真正触发一次上传。一串操作合并成一次网络请求。

function scheduleAutoPush(){
  clearTimeout(pushTimer);
  pushTimer = setTimeout(autoPushNow, 8000);  // 连续操作只保留最后一次
}
async function autoPushNow(){
  const c = cfg();
  if(!c.token || !c.autoPush || busy) return;
  if((Store.state.meta.lastLocalWrite||0) <= c.syncedAt) return; // 没有新改动
  const remote = await fetchRemote();           // 先 GET 云端对账
  if(remote && Date.parse(remote.exportedAt) > c.syncedAt){
    toast('云端有较新数据，已暂停自动上传，请手动「从云端下载」'); return;
  }
  await push();
}

凭证安全：token 永不上云

GitHub token（ghp_ 开头）只存在本机浏览器的 meta 里，随 Authorization: Bearer 请求头发给 GitHub。打包同步数据时，所有 cs 开头的配置键（token、gistId、同步时间戳）都被过滤掉，永远不会被同步到云端或别的设备：

meta: Object.keys(Store.state.meta)
  .filter(k => k.indexOf('cs') !== 0)   // 过滤所有凭证相关键
  .map(k => ({ key: k, value: Store.state.meta[k] }))

06冲突保护：两个时间戳对账

最关键的问题：手机电脑都快，谁的数据算准？

系统维护两个时间戳，它们的差值就是「对账」的依据：

时间戳含义谁在维护
lastLocalWrite我最后一次改数据的时间写队列，每次用户写入自动盖戳
csSyncedAt我上次和云端对齐的时间同步模块，每次上传/下载成功后更新

自动上传前先 GET 一次云端，比较云端数据的 exportedAt：

  • 云端 ≤ 我的 csSyncedAt → 云端的内容我都见过，是我的数据，放心推
  • 云端 > 我的 csSyncedAt → 有别的设备推过一个我没见过的版本。此时如果我盲目上传，就会用旧数据把云端整个盖掉，另一台设备的打卡直接丢失。所以选择「暂停自动上传 + 提示手动下载」，宁停不盲写。手动上传遇到同样情况也会弹 confirm 双重确认
为什么「云端更新」反而要停下来？ 场景：你在手机打卡（A 设备已推送到云端），然后打开电脑（B 设备还停留在上次同步的状态）随手改了一笔。如果 B 直接自动上传，它就会用没见过 A 数据的旧仓库把云端盖掉——你手机的打卡就丢了。停下来不是防冲突本身，是防丢数据。

silent 写通道：防自激循环

同步动作本身也要写库（更新 csSyncedAt）。如果这些写入也触发「8 秒后自动上传」，就会形成 push → 写时间戳 → 触发 push → 再写 → 无限循环，把 GitHub 的限流配额烧光。所以写队列的 silent 参数让同步内部的写入走静默通道——不更新 lastLocalWrite、不触发定时器。只有真正打卡、改计划这类用户操作，才会驱动上传。

07上手指南

五分钟完成多设备配置，之后全自动。

生成 GitHub token

GitHub → Settings → Developer settings → Personal access tokens → Tokens (classic) → Generate new token，勾选 gist 权限，复制 ghp_ 开头的字符串。

在旧设备启用同步

在有打卡数据的设备上打开工作台 → 计划页 → 「云同步」卡片 → 粘贴 token → 点「启用云同步」。

迁移历史数据（仅换源时需要）

如果旧数据在本地 file:// 打开的版本里：先「导出 JSON」→ 在线上网址「导入恢复」→ 它会自动上传到云端。线上是新的源、新的空仓库，这一步不能省。

其他设备接入

打开同一网址 → 粘贴同一 token → 点一次「从云端下载」（同 token 会自动关联到已有的那份云端数据，无需手填 Gist 编号，也不会新建第二个）。之后所有设备就全自动同步了。

日常使用

正常打卡即可。每次改动 8 秒后自动上传；打开另一台设备时如有云端新数据，会提示你先下载。token 建议定期在 GitHub 后台轮换。

常见问题 GitHub API 国内访问偶尔较慢，同步失败重试即可；若提示「云端数据更新」，先「从云端下载」再继续操作；沙箱链接失效时重新部署一次即可恢复，打卡数据不受影响（数据在本机和 Gist，不在沙箱）。
设备下载后显示「未连接」？这是旧版本 bug：「从云端下载 / 导入备份」会顺带清掉本机 token 与 Gist 编号。当前版本下载与导入都会保留云同步配置；若之前已断连，重新粘贴 token 点「从云端下载」即可（会自动关联回原 Gist）。

08设计取舍与局限

为什么不做实时双向合并。

这套方案是整包 last-write-wins（最后写入者胜）+ 人工确认兜底，不是 Git 那种增量合并。极端场景：两台设备同时离线打卡再同时上线——后推的那台会弹确认框，你要在「上传覆盖」和「下载覆盖」之间二选一，不会自动合并两边的打卡项。

对单人使用的打卡场景，这个取舍是划算的：

方案冲突处理复杂度额外依赖
本方案（整包 + 时间戳）人工二选一，绝不丢已见数据约 180 行，零依赖无
字段级合并自动合并需 CRDT / 向量时钟通常需后端

真要双向合并，得引入 CRDT 或给每条记录记向量时钟——在一个零依赖单文件应用里不值得。这个复杂度预算，留给了真正每天在用的功能：打卡的速度、拖拽的手感、统计的直观。

一句话总结 部署解决「文件跟着网址走」，Gist 解决「数据跟着 token 走」，时间戳对账保证「谁都没见过的改动不会被覆盖」。
